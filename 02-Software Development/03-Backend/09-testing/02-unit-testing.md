## Summary
Unit testing focuses on verifying the smallest testable parts of an application (functions, methods, or structs) in isolation from their dependencies. In Go, unit tests are characterized by their speed, reliability, and use of the built-in `testing` package to ensure code correctness at a granular level.

## Detailed Explanation
Unit tests are the foundation of the testing pyramid. They are designed to be fast, enabling developers to run them frequently during development.

### Key Characteristics
- **Isolation**: Units are tested independently. External dependencies like databases, networks, or file systems are replaced with mocks or stubs.
- **Speed**: Thousands of unit tests should execute in seconds.
- **Determinism**: A unit test should produce the same result every time it runs, given the same input.

### Unit Testing in Go
Go provides a robust standard library for testing through the `testing` package. Conventionally, test files are named with a `_test.go` suffix and reside in the same package as the code they test.

#### The `testing` Package
- **`t.Error` / `t.Errorf`**: Marks the test as failed but continues execution.
- **`t.Fatal` / `t.Fatalf`**: Marks the test as failed and stops execution immediately.
- **`t.Run`**: Enables subtests, which are useful for table-driven testing.

#### Table-Driven Tests
A common pattern in Go where you define a slice of anonymous structs containing inputs and expected outputs, then iterate over them in a single test function.

#### Mocking and Stubbing
To isolate units, Go developers use interfaces.
- **Testify**: A popular toolkit that provides assertion functions (`assert`, `require`) and a mocking framework.
- **GoMock**: A mock framework from Google that generates mock implementations of interfaces using a source-code generator.

## Go-specific Examples

### Table-Driven Unit Test with `testify`
```go
package calculator

import (
    "testing"
    "github.com/stretchr/testify/assert"
)

func Add(a, b int) int {
    return a + b
}

func TestAdd(t *testing.T) {
    tests := []struct {
        name     string
        a, b     int
        expected int
    }{
        {"positive numbers", 2, 3, 5},
        {"negative numbers", -1, -1, -2},
        {"zero value", 0, 5, 5},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            result := Add(tt.a, tt.b)
            assert.Equal(t, tt.expected, result, "they should be equal")
        })
    }
}
```

### Mocking with `gomock`
Suppose we have a `Fetcher` interface:
```go
type Fetcher interface {
    FetchData(id string) (string, error)
}

type Service struct {
    fetcher Fetcher
}

func (s *Service) GetDetails(id string) string {
    data, err := s.fetcher.FetchData(id)
    if err != nil {
        return "Error"
    }
    return "Data: " + data
}
```

In the test file:
```go
func TestGetDetails(t *testing.T) {
    ctrl := gomock.NewController(t)
    defer ctrl.Finish()

    mockFetcher := NewMockFetcher(ctrl) // Generated by mockgen
    service := &Service{fetcher: mockFetcher}

    mockFetcher.EXPECT().FetchData("123").Return("success", nil)

    result := service.GetDetails("123")
    assert.Equal(t, "Data: success", result)
}
```

## Interview Questions
**Q: Why are interfaces important for unit testing in Go?**
**A:** Interfaces allow for Dependency Injection. By depending on an interface rather than a concrete implementation, you can swap out real dependencies (like a database) with mocks during testing, ensuring the unit is tested in isolation.

**Q: What is the difference between `t.Error` and `t.Fatal`?**
**A:** `t.Error` logs an error message and fails the test but allows the rest of the test function (and other tests) to continue. `t.Fatal` logs the message and immediately aborts the current test function.

**Q: How do you handle side effects in unit tests?**
**A:** Side effects (like writing to a file or making an API call) should be abstracted behind interfaces. In unit tests, you use mocks to simulate these side effects and verify that the unit interacts with the dependency correctly without actually performing the side effect.
