# Good JWT Secret

## Summary
The security of a signed JWT (JWS) relies entirely on the strength of the secret key used to generate the signature. For **HS256** (HMAC-SHA256), a weak secret allows attackers to offline brute-force the key and forge tokens, granting them full administrative access. A good secret must have high entropy and sufficient length (minimum 256 bits/32 bytes).

## Detailed Explanation

### 1. Entropy and Length Requirements
*   **Algorithm Requirement**: The HS256 algorithm uses the SHA-256 hash function. RFC 7518 states that the key size "MUST be" at least as large as the hash output.
    *   **Minimum**: 256 bits (32 bytes).
    *   **Recommended**: 512 bits (64 bytes) to future-proof against increased computing power.
*   **Entropy**: A 32-character string like `"supersecretpassword123!"` is **NOT** secure because it lacks entropy (randomness). A secure secret should be a random byte sequence generated by a CSPRNG (Cryptographically Secure Pseudo-Random Number Generator).

### 2. The Risks of Weak Secrets (Offline Brute-Force)
JWTs are often public (stored in local storage, sent in headers). An attacker can easily obtain a valid JWT.
*   **The Attack**: Since the signature is calculated as `HMAC(Header + Payload, Secret)`, an attacker can run a local tool (like `hashcat` or `John the Ripper`) to try millions of potential secrets per second against the captured signature.
*   **The Consequence**: If the secret is guessed, the attacker can create a new JWT with `{"role": "admin"}`, sign it with the cracked secret, and the server will accept it as valid.

### 3. Best Practices
*   **Management**: Use a dedicated Secret Manager (Vault, AWS Secrets Manager) and inject secrets as environment variables. Never commit them to Git.
*   **Rotation**: Implement key rotation. Support multiple valid keys (via `kid` header) to allow a smooth transition during rotation.
*   **Algorithm Choice**:
    *   **HS256 (Symmetric)**: Fast, simple, but requires the secret to be shared with every service that verifies the token.
    *   **RS256/ES256 (Asymmetric)**: Uses a Private Key to sign and a Public Key to verify. Safer for distributed systems as the Private Key never leaves the auth server.

## Go (Golang) Application

### Secure Secret Loading & Signing
Using `github.com/golang-jwt/jwt/v5`.

```go
package main

import (
	"crypto/rand"
	"encoding/base64"
	"errors"
	"fmt"
	"os"
	"time"

	"github.com/golang-jwt/jwt/v5"
)

// GenerateRandomKey creates a high-entropy 64-byte key
func GenerateRandomKey() string {
	key := make([]byte, 64)
	rand.Read(key)
	return base64.StdEncoding.EncodeToString(key)
}

func getSecret() ([]byte, error) {
	// In production, load this from ENV or Secret Manager
	secretEnv := os.Getenv("JWT_SECRET")
	if secretEnv == "" {
		return nil, errors.New("JWT_SECRET is not set")
	}

	secret, err := base64.StdEncoding.DecodeString(secretEnv)
	if err != nil {
		return nil, fmt.Errorf("failed to decode secret: %v", err)
	}

	if len(secret) < 32 {
		return nil, errors.New("secret is too short (min 32 bytes required)")
	}

	return secret, nil
}

func CreateToken(userID string) (string, error) {
	key, err := getSecret()
	if err != nil {
		return "", err
	}

	// Create claims
	claims := jwt.MapClaims{
		"sub": userID,
		"iat": jwt.NewNumericDate(time.Now()),
		"exp": jwt.NewNumericDate(time.Now().Add(time.Hour * 1)),
	}

	// Sign
	token := jwt.NewWithClaims(jwt.SigningMethodHS256, claims)
	return token.SignedString(key)
}
```

## Interview Questions

**Q1: Why is a secret length of 32 characters not necessarily enough for HS256?**
**A**: Length != Entropy. A 32-character phrase like "this-is-my-secret-key-for-prod" has low entropy and is susceptible to dictionary attacks. A 32-byte key generated by a CSPRNG has high entropy and is mathematically infeasible to guess.

**Q2: What is the main security advantage of RS256 over HS256?**
**A**: RS256 is asymmetric. The verification process only requires the Public Key. This means if a Resource Server (API) is compromised and the key leaks, the attacker can only *verify* tokens, not *forge* new ones. With HS256, a compromised API means the Signing Key is leaked, allowing full forgery.

**Q3: How would you rotate a JWT secret without logging out all active users?**
**A**: By maintaining a list of valid keys. The Auth Server signs new tokens with the *new* key but accepts tokens signed by the *old* key for a grace period (e.g., 24 hours). The `kid` (Key ID) header in the JWT tells the server which key to use for verification.
