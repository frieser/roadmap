## Summary
`Rc<T>` (Reference Counted) provides shared ownership of a value of type `T`. It enables multiple owners for the same data by keeping a running count of references. It is **not** thread-safe and creates immutable references by default. It allows data to live as long as at least one owner exists.

## Detailed Explanation

### 1. Shared Ownership
In Rust's standard ownership model, a value has a single owner. `Rc<T>` bends this rule.
- When you clone an `Rc`, it doesn't copy the data. It increments a counter.
- When an `Rc` is dropped, it decrements the counter.
- When the count reaches zero, the data is cleaned up.

### 2. Single-Threaded Only
`Rc` uses non-atomic integer operations for performance.
- It does **not** implement the `Send` or `Sync` traits.
- Attempting to pass an `Rc` to another thread will result in a compile-time error.
- Use `Arc` (Atomic Reference Counted) for multi-threaded scenarios.

### 3. Interior Mutability
Since `Rc` only gives you shared (immutable) references, it is often combined with `RefCell<T>` to allow mutation.
- Pattern: `Rc<RefCell<T>>` allows multiple owners to mutate the same data (checked at runtime).

## Rust Application

### Basic Usage (Graph/Tree Structure)
A classic use case is a graph where a node might be owned by multiple edges.

```rust
use std::rc::Rc;

struct Node {
    value: i32,
    next: Option<Rc<Node>>,
}

fn main() {
    let leaf = Rc::new(Node { value: 10, next: None });
    
    // Multiple nodes pointing to the same 'leaf'
    let node1 = Node { value: 1, next: Some(Rc::clone(&leaf)) };
    let node2 = Node { value: 2, next: Some(Rc::clone(&leaf)) }; // Shared!

    println!("Leaf strong count: {}", Rc::strong_count(&leaf)); // Output: 3
}
```

### With RefCell for Mutation
```rust
use std::rc::Rc;
use std::cell::RefCell;

fn main() {
    let shared_data = Rc::new(RefCell::new(5));

    let owner1 = Rc::clone(&shared_data);
    let owner2 = Rc::clone(&shared_data);

    *owner1.borrow_mut() += 10;
    
    println!("Modified via owner1: {}", owner2.borrow()); // Output: 15
}
```

## Interview Questions

### Q: Why isn't `Rc` thread-safe?
**A:** It uses standard arithmetic operations (`+= 1`, `-= 1`) to manage its reference count. If two threads tried to clone/drop the `Rc` simultaneously, a race condition could occur, causing the count to become incorrect and leading to memory leaks or use-after-free errors.

### Q: What is the difference between `Rc::clone(&x)` and `x.clone()`?
**A:** Functionally they are the same, but `Rc::clone(&x)` is idiomatic. It explicitly signals "I am incrementing the reference count," whereas `x.clone()` might look like a potentially expensive deep copy of the underlying data.

### Q: Can `Rc` create reference cycles?
**A:** Yes. If two `Rc` pointers refer to each other (usually via `RefCell`), the reference count will never reach zero, causing a memory leak. Rust provides `Weak<T>` (via `Rc::downgrade`) to break these cycles.
