## Summary
Rust's async model relies on **cooperative multitasking** using **Futures**, **Async/Await** syntax, and **Executors**. Unlike Green Threads (Go), Rust has no built-in runtime; `Future`s are state machines that must be polled by an external executor (like `tokio`) to make progress. This zero-cost abstraction allows for highly efficient I/O-bound applications.

## Detailed Explanation

### 1. The `Future` Trait
The core building block. A `Future` represents a value that is not yet ready.
```rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```
- **Poll-based**: Futures do nothing until polled.
- **`Poll::Pending`**: Means "not ready, I'll wake you up later".
- **`Poll::Ready(val)`**: The computation is complete.

### 2. Async/Await and Desugaring
- **`async fn`**: Syntactic sugar that transforms a function into a state machine that implements `Future`.
- **`.await`**: Yields control back to the executor if the future is not ready. It marks a "suspension point" where the state is saved.

### 3. Executors and Reactors
- **Executor**: The runtime engine (e.g., Tokio, async-std) that maintains a queue of tasks and calls `poll()` on them.
- **Reactor**: Handles low-level I/O events (like network packets) and triggers `Waker`s to notify the Executor that a task is ready to be polled again.

### 4. Pinning (`Pin<T>`)
Async functions often create self-referential structs (e.g., holding a reference to a local variable across an `.await` point).
- **Problem**: If such a struct is moved in memory, the pointer becomes invalid.
- **Solution**: `Pin<&mut T>` prevents the value `T` from being moved, ensuring memory safety for these self-referential futures.

## Rust Application

### Basic Async Function (Tokio)
Using `tokio` as the executor (runtime).

```rust
use tokio::time::{sleep, Duration};

#[tokio::main]
async fn main() {
    let f1 = do_work("Task 1", 100);
    let f2 = do_work("Task 2", 50);

    // Run concurrently using join!
    let (res1, res2) = tokio::join!(f1, f2);

    println!("Done: {}, {}", res1, res2);
}

async fn do_work(name: &str, ms: u64) -> String {
    println!("Starting {}", name);
    // .await yields control here, allowing other tasks to run
    sleep(Duration::from_millis(ms)).await; 
    println!("Finished {}", name);
    format!("{} Result", name)
}
```

## Interview Questions

### Q: How does Rust's async differ from Go's Goroutines?
**A:** Rust uses "Stackless Coroutines" (State Machines) compiled into the binary, with no runtime overhead by default. You choose your executor. Go uses "Stackful Coroutines" (Green Threads) with a built-in runtime and garbage collector. Rust is zero-cost but has a steeper learning curve (Pinning, Lifetimes).

### Q: What is the purpose of `Pin`?
**A:** `Pin` guarantees that an object remains at a fixed memory address. This is required for `Future`s generated by `async`/`await` because they may contain self-referential pointers (pointing to their own internal state). If the future moved, those pointers would dangle.

### Q: What happens if you block inside an async function?
**A:** Blocking the thread (e.g., `std::thread::sleep` or heavy CPU work) stops the Executor from polling *any* other tasks on that thread. This creates a bottleneck. You should use async-aware functions (like `tokio::time::sleep`) or `spawn_blocking` for CPU-intensive tasks.
