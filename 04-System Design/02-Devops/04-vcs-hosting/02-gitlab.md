# GitLab for DevOps

GitLab is a complete DevOps platform delivered as a single application. Unlike GitHub, which started as hosting and added CI/CD later, GitLab was built with CI/CD as a core component from the beginning. It covers the entire lifecycle, from planning and source code management to monitoring and security.

## Summary

GitLab is famous for its **integrated CI/CD**, defined in `.gitlab-ci.yml`. It supports complex pipelines with **Directed Acyclic Graphs (DAGs)**, **Auto DevOps** (automatically detecting and building apps), and built-in **Container Registry**. For enterprise DevOps, its ability to run as a self-managed instance (`GitLab Omnibus`) offers total control over data and infrastructure.

## Detailed Explanation

### 1. GitLab CI/CD
*   **.gitlab-ci.yml**: The configuration file located in the root of the repo.
*   **GitLab Runner**: The agent that executes jobs. It interacts with the GitLab server to pick up jobs. It can execute via Shell, Docker, Kubernetes, or SSH.
*   **Pipelines**: Composed of Stages (Build, Test, Deploy). Jobs in the same stage run in parallel.
*   **Environments**: Tracks deployments (e.g., Staging, Production) and provides a history of what is deployed where.

### 2. Key Features
*   **Auto DevOps**: A pre-configured pipeline that detects your language (e.g., Go, Python), builds it using Cloud Native Buildpacks, and deploys it to Kubernetes.
*   **Merge Request (MR) Reviews**: Supports "Review Apps," where a dynamic environment is spun up for every merge request to test changes live.
*   **Terraform State Management**: GitLab can act as a backend for Terraform state files, securing them with access controls.

## Go Implementation Example

The `xanzy/go-gitlab` library is the community-standard Go client for the GitLab API. It is useful for automating project creation, user management, and triggering pipelines.

```go
package main

import (
	"fmt"
	"log"

	"github.com/xanzy/go-gitlab"
)

func main() {
	// 1. Create a client instance
	// Supports both GitLab.com and self-hosted instances
	git, err := gitlab.NewClient("YOUR_PRIVATE_TOKEN", gitlab.WithBaseURL("https://gitlab.com/api/v4"))
	if err != nil {
		log.Fatalf("Failed to create client: %v", err)
	}

	// 2. Search for a project
	opt := &gitlab.ListProjectsOptions{
		Search: gitlab.Ptr("devops"),
		Simple: gitlab.Ptr(true),
	}
	projects, _, err := git.Projects.ListProjects(opt)
	if err != nil {
		log.Fatal(err)
	}

	for _, p := range projects {
		fmt.Printf("Found Project: %s (ID: %d)\n", p.Name, p.ID)
	}

	// 3. Trigger a Pipeline Programmatically
	// Useful for triggering downstream builds or ChatOps
	projectID := 12345
	pipelineOpt := &gitlab.CreatePipelineOptions{
		Ref: gitlab.Ptr("main"),
		Variables: []*gitlab.PipelineVariable{
			{Key: "DEPLOY_TARGET", Value: "staging"},
		},
	}

	pipeline, _, err := git.Pipelines.CreatePipeline(projectID, pipelineOpt)
	if err != nil {
		log.Printf("Error triggering pipeline: %v", err)
	} else {
		fmt.Printf("Pipeline started! ID: %d, Status: %s\n", pipeline.ID, pipeline.Status)
	}
}
```

## Interview Questions

**Q: What is a GitLab Runner and what are its executors?**
**A:** A GitLab Runner is an application that runs jobs in a pipeline. Executors define *how* the job runs:
*   **Shell**: Runs directly on the runner's OS (fast, but no isolation).
*   **Docker**: Runs each job in a separate Docker container (clean environment, most common).
*   **Kubernetes**: Spawns a pod for each job (highly scalable).
*   **VirtualBox/Parallels**: Creates a VM for each job.

**Q: Explain the difference between `artifacts` and `cache` in GitLab CI.**
**A:**
*   **Artifacts**: Files generated by a job (e.g., binaries, test reports) that are sent to the GitLab server and passed to *subsequent stages*. They expire after a set time.
*   **Cache**: Files (e.g., `node_modules`, `go mod download`) stored locally on the runner to speed up *future runs* of the same job. They are not guaranteed to be present.

**Q: What is a "Review App" in GitLab?**
**A:** A Review App is a dynamic environment created automatically for a specific Merge Request. It deploys the code changes to a temporary URL, allowing developers and stakeholders to view and test the changes live before merging them into the main branch. When the MR is merged or closed, the environment is destroyed.
