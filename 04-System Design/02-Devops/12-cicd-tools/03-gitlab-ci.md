# GitLab CI

GitLab CI/CD is part of the GitLab single-application platform. It is famous for its robust pipeline visualization and native support for Directed Acyclic Graphs (DAG) within pipelines.

## Summary

Configuration is defined in `.gitlab-ci.yml`. The architecture relies on **GitLab Runners** which execute jobs. A standout feature is **Auto DevOps**, which can automatically detect, build, test, and deploy applications (using Herokuish buildpacks) without explicit configuration.

## Detailed Explanation

### 1. Key Concepts
*   **Pipeline**: The top-level component. Contains Stages.
*   **Stage**: A grouping of jobs (Build, Test, Deploy). Jobs in the same stage run in parallel. The next stage only starts if the previous one succeeds.
*   **Job**: The smallest unit of work. Defined with a `script`.
*   **DAG (Directed Acyclic Graph)**: Using the `needs` keyword, jobs can depend directly on other jobs regardless of stage, speeding up execution.

### 2. Artifacts vs Cache
*   **Artifacts**: Passed between stages. Permanent (until expiration).
*   **Cache**: Used to speed up builds (e.g., `go mod download`). Best effort, not guaranteed.

## Go Implementation Example

Advanced GitLab pipelines often use **Dynamic Child Pipelines**. You can write a Go program that *generates* a YAML configuration file based on dynamic logic (e.g., "only generate test jobs for changed directories"), and GitLab will execute that generated YAML.

### Pipeline Generator in Go
```go
package main

import (
	"fmt"
	"os"
)

func main() {
	// A simple generator that creates a pipeline with dynamic jobs
	yamlContent := `
stages:
  - build

build-job:
  stage: build
  script:
    - echo "Generated by Go!"
`
	// Write to a file that GitLab will ingest
	err := os.WriteFile("generated-ci.yml", []byte(yamlContent), 0644)
	if err != nil {
		panic(err)
	}
	fmt.Println("Pipeline generated successfully.")
}
```

### .gitlab-ci.yml Usage
```yaml
generate-pipeline:
  stage: build
  script: go run generator.go
  artifacts:
    paths:
      - generated-ci.yml

trigger-child:
  stage: test
  trigger:
    include:
      - artifact: generated-ci.yml
        job: generate-pipeline
```

## Interview Questions

**Q: What is the `needs` keyword in GitLab CI and how does it optimize pipelines?**
**A:** `needs` enables **DAG (Directed Acyclic Graph)** execution. By default, jobs wait for the entire previous stage to finish. With `needs: ["job_a"]`, a job can start immediately after `job_a` finishes, even if other jobs in the previous stage are still running. This significantly reduces total pipeline time.

**Q: Explain "GitLab Runner Executors".**
**A:** The Executor determines environment the job runs in.
*   **Shell**: Runs on the host machine. Fast, but no isolation.
*   **Docker**: Runs in a container. Clean environment, easy dependency management.
*   **Kubernetes**: Creates a Pod for each job. Highly scalable for large teams.

**Q: What are "Review Apps"?**
**A:** Review Apps are dynamic environments created for every Merge Request. GitLab CI deploys the code branch to a temporary environment (e.g., a K8s namespace) and provides a link. This allows stakeholders to test changes live before merging.
