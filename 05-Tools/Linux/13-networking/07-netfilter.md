# Netfilter and Firewalls

## Summary
**Netfilter** is the core kernel-level framework in Linux that provides the infrastructure for packet filtering, network address translation (NAT), and connection tracking. It operates through a series of "hooks" in the networking stack where packet handlers can be registered. User-space utilities such as **iptables**, **nftables**, **ufw**, and **firewalld** act as interfaces to configure the rules processed by Netfilter.

## Detailed Explanation

### 1. Netfilter Hooks
Netfilter defines five key points (hooks) where programs can intercept and manipulate network traffic:
- **NF_IP_PRE_ROUTING**: Triggered as soon as a packet enters the network stack.
- **NF_IP_LOCAL_IN**: Triggered if the packet is destined for the local system.
- **NF_IP_FORWARD**: Triggered if the packet is destined for another host.
- **NF_IP_LOCAL_OUT**: Triggered for packets generated by the local system.
- **NF_IP_POST_ROUTING**: Triggered just before a packet leaves the system.

### 2. iptables: The Traditional Interface
`iptables` organizes rules into **Tables**, which contain **Chains**, which in turn contain individual **Rules**.

#### Key Tables:
- **filter**: Default table for packet filtering. Chains: `INPUT`, `FORWARD`, `OUTPUT`.
- **nat**: Used for address translation. Chains: `PREROUTING`, `POSTROUTING`, `OUTPUT`.
- **mangle**: For specialized packet alteration (TTL, TOS). All chains.
- **raw**: For configuring exemptions from connection tracking. `PREROUTING`, `OUTPUT`.

#### Bash Examples:
```bash
# Allow all traffic on loopback
sudo iptables -A INPUT -i lo -j ACCEPT

# Allow established and related connections (Stateful Inspection)
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# Allow SSH (Port 22)
sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT

# Port Forwarding (NAT)
sudo iptables -t nat -A PREROUTING -i eth0 -p tcp --dport 80 -j DNAT --to-destination 192.168.1.10:80

# List rules with details
sudo iptables -L -v -n
```

### 3. nftables: The Modern Standard
`nftables` is the successor to `iptables`, providing a more efficient VM-based execution and a unified syntax for IPv4, IPv6, ARP, and bridging.

#### Bash Examples:
```bash
# Create a unified table for IPv4 and IPv6
sudo nft add table inet filter

# Create an input chain with a base hook
sudo nft add chain inet filter input { type filter hook input priority 0 \; policy drop \; }

# Allow SSH traffic
sudo nft add rule inet filter input tcp dport 22 accept

# List current ruleset in a human-readable format
sudo nft list ruleset
```

### 4. High-Level Frontends
Administrators often use easier-to-manage wrappers:
- **UFW (Uncomplicated Firewall)**: Popular on Debian/Ubuntu. Focuses on simple "allow/deny" logic.
- **firewalld**: Default on RHEL/Fedora. Uses "Zones" and "Services" to manage dynamic rulesets without breaking active connections.

#### firewalld Zone Example:
```bash
# Move an interface to the 'work' zone
sudo firewall-cmd --zone=work --add-interface=eth0

# Allow HTTPS permanently
sudo firewall-cmd --permanent --zone=public --add-service=https
sudo firewall-cmd --reload
```

## Interview Questions

1. **Q: What is the difference between a REJECT and a DROP target?**
   - **A:** `DROP` simply discards the packet without sending any notification back to the sender, making the port appear "filtered" (stealth). `REJECT` discards the packet and sends an ICMP "port unreachable" error back, explicitly informing the sender that the connection was refused.

2. **Q: How does Netfilter handle Connection Tracking (conntrack)?**
   - **A:** Netfilter uses the `conntrack` module to keep track of the state of network connections (NEW, ESTABLISHED, RELATED, INVALID). This allows for stateful firewalls that can automatically allow return traffic for established connections.

3. **Q: In which table and chain would you implement Source NAT (SNAT)?**
   - **A:** SNAT should be implemented in the `nat` table within the `POSTROUTING` chain, as the source address must be changed after the routing decision is made, just before the packet leaves the interface.

4. **Q: Why should you migrate from iptables to nftables?**
   - **A:** `nftables` offers significantly better performance through its internal virtual machine, reduced kernel code footprint, a more consistent syntax across different protocols (no more separate `ip6tables` or `arptables`), and the ability to perform atomic ruleset updates.

5. **Q: What is the purpose of the "mangle" table?**
   - **A:** The `mangle` table is used for specialized packet modification. Common use cases include changing the Type of Service (ToS) bits, modifying the Time to Live (TTL) of a packet, or marking packets (fwmark) for advanced routing and traffic control (QoS).
