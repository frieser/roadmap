# Volume Mounts

## Summary

Docker volumes are the preferred mechanism for persisting data generated by containers. Volumes are managed by Docker, stored outside the container's filesystem (in `/var/lib/docker/volumes/`), and exist independently of the container lifecycle. They offer better performance than bind mounts on Docker Desktop, support volume drivers for cloud storage, and can be shared between containers.

## Detailed Explanation

### What Are Volumes?

```
HOST FILESYSTEM:
/var/lib/docker/volumes/
└── mydata/
    └── _data/
        ├── file1.txt
        └── database/

CONTAINER VIEW:
/app/data/
├── file1.txt
└── database/

# Volume "mydata" is mounted at /app/data inside the container
# Data persists even if container is removed
# Managed entirely by Docker
```

### Creating and Using Volumes

```bash
# Create a volume
docker volume create mydata

# List volumes
docker volume ls
# DRIVER    VOLUME NAME
# local     mydata

# Inspect volume
docker volume inspect mydata
# [
#   {
#     "Name": "mydata",
#     "Driver": "local",
#     "Mountpoint": "/var/lib/docker/volumes/mydata/_data",
#     "Labels": {},
#     "Scope": "local"
#   }
# ]

# Use volume in container (short syntax)
docker run -d \
  --name postgres \
  -v mydata:/var/lib/postgresql/data \
  postgres:15

# Use volume in container (long syntax)
docker run -d \
  --name postgres \
  --mount type=volume,source=mydata,target=/var/lib/postgresql/data \
  postgres:15
```

### Anonymous vs Named Volumes

```bash
# NAMED VOLUME - Recommended
docker volume create mydata
docker run -v mydata:/app/data myapp
# Easy to reference, backup, and manage

# ANONYMOUS VOLUME - Created automatically
docker run -v /app/data myapp
# Docker creates random name like abc123def456
# Harder to manage, often forgotten

# List all volumes (named and anonymous)
docker volume ls
# DRIVER    VOLUME NAME
# local     mydata                                    <- Named
# local     7f4a3b2c1d0e9f8a7b6c5d4e3f2a1b0c9d8e7f6a <- Anonymous

# Remove anonymous volumes when removing container
docker rm -v mycontainer
```

### Volume Options

```bash
# Read-only volume
docker run -v mydata:/app/data:ro myapp
docker run --mount type=volume,source=mydata,target=/app/data,readonly myapp

# Volume with driver options (local driver)
docker volume create --driver local \
  --opt type=nfs \
  --opt o=addr=192.168.1.1,rw \
  --opt device=:/path/to/dir \
  nfs-volume

# Tmpfs-like options (for local driver)
docker volume create --driver local \
  --opt type=tmpfs \
  --opt device=tmpfs \
  --opt o=size=100m,uid=1000 \
  temp-volume
```

### Sharing Volumes Between Containers

```bash
# Create shared volume
docker volume create shared_data

# Container A writes data
docker run -d \
  --name writer \
  -v shared_data:/data \
  ubuntu:22.04 \
  bash -c 'while true; do date >> /data/log.txt; sleep 1; done'

# Container B reads data
docker run --rm \
  -v shared_data:/data:ro \
  ubuntu:22.04 \
  tail -f /data/log.txt

# Common pattern: sidecar containers
# Main app writes logs, sidecar processes them
docker run -d --name app -v logs:/var/log/app myapp
docker run -d --name log-shipper -v logs:/logs:ro fluentd
```

### Volume Lifecycle

```bash
# Volumes persist independently of containers

# Create container with volume
docker run -d --name db -v postgres_data:/var/lib/postgresql/data postgres:15

# Stop and remove container
docker rm -f db
# Volume still exists!

docker volume ls
# DRIVER    VOLUME NAME
# local     postgres_data

# Start new container with same volume
docker run -d --name db2 -v postgres_data:/var/lib/postgresql/data postgres:15
# All data is still there!

# Remove volume (only when no container uses it)
docker volume rm postgres_data
# Error response: volume is in use

docker rm db2
docker volume rm postgres_data
# Success

# Remove all unused volumes
docker volume prune
# WARNING! This will remove all local volumes not used by at least one container.
```

### Volume Backup and Restore

```bash
# BACKUP: Create tar archive of volume
docker run --rm \
  -v postgres_data:/data \
  -v $(pwd):/backup \
  alpine tar czf /backup/postgres_backup.tar.gz -C /data .

# RESTORE: Extract tar archive to volume
docker volume create postgres_data_restored
docker run --rm \
  -v postgres_data_restored:/data \
  -v $(pwd):/backup \
  alpine tar xzf /backup/postgres_backup.tar.gz -C /data

# COPY between volumes
docker run --rm \
  -v source_volume:/source:ro \
  -v dest_volume:/dest \
  alpine sh -c 'cp -a /source/. /dest/'

# Database-specific backup (better for databases)
docker exec postgres pg_dump -U user dbname > backup.sql
docker exec -i postgres psql -U user dbname < backup.sql
```

### Docker Compose Volumes

```yaml
# docker-compose.yml
version: '3.8'

services:
  postgres:
    image: postgres:15
    volumes:
      # Named volume
      - postgres_data:/var/lib/postgresql/data
      # Bind mount for init scripts
      - ./init:/docker-entrypoint-initdb.d:ro

  app:
    build: .
    volumes:
      # Named volume (shared with postgres? usually not)
      - app_data:/app/data
      # Anonymous volume (not recommended)
      - /app/cache

volumes:
  postgres_data:
    # Uses default local driver
  
  app_data:
    driver: local
    driver_opts:
      type: none
      device: /host/path/to/data
      o: bind

  # External volume (created outside compose)
  external_data:
    external: true
```

### Volume Drivers

```bash
# Local driver (default)
docker volume create --driver local mydata

# Popular volume drivers:

# REX-Ray (multi-cloud storage)
docker plugin install rexray/s3fs
docker volume create -d rexray/s3fs mybucket

# Azure File Storage
docker plugin install docker4x/cloudstor:azure
docker volume create -d docker4x/cloudstor:azure \
  --opt share=myshare azure_volume

# NFS
docker volume create \
  --driver local \
  --opt type=nfs \
  --opt o=addr=192.168.1.1,rw \
  --opt device=:/exported/path \
  nfs_volume

# CIFS/SMB
docker volume create \
  --driver local \
  --opt type=cifs \
  --opt device=//server/share \
  --opt o=username=user,password=pass \
  cifs_volume
```

### Volumes vs Bind Mounts

```yaml
# VOLUMES (preferred for data persistence)
advantages:
  - Managed by Docker
  - Better performance on Docker Desktop
  - Can use volume drivers for cloud storage
  - Easy backup/migrate with Docker commands
  - Safe from accidental host changes
  - Work on all Docker platforms

syntax:
  - "-v myvolume:/path"
  - "--mount type=volume,source=myvolume,target=/path"

use_for:
  - Databases
  - Application data
  - Anything that should persist

# BIND MOUNTS (direct host access)
advantages:
  - Direct access to host files
  - Changes reflect immediately both ways
  - Access to any host path

syntax:
  - "-v /host/path:/container/path"
  - "--mount type=bind,source=/host/path,target=/container/path"

use_for:
  - Development (live code reloading)
  - Configuration files
  - When host path access is required
```

### Best Practices

```yaml
# 1. USE NAMED VOLUMES
# Bad: Anonymous volumes are hard to manage
docker run -v /app/data myapp

# Good: Named volumes are clear and manageable
docker run -v myapp_data:/app/data myapp

# 2. ONE VOLUME PER PURPOSE
# Bad: Everything in one volume
docker run -v app_all:/app myapp

# Good: Separate concerns
docker run \
  -v app_data:/app/data \
  -v app_logs:/app/logs \
  -v app_uploads:/app/uploads \
  myapp

# 3. USE READ-ONLY WHEN APPROPRIATE
docker run -v config:/app/config:ro myapp

# 4. DOCUMENT VOLUME REQUIREMENTS
# In Dockerfile:
VOLUME /app/data
# In compose:
volumes:
  app_data:
    labels:
      com.example.description: "Application data"
      com.example.backup: "daily"

# 5. IMPLEMENT BACKUP STRATEGY
# Regular automated backups for important volumes
```

## Interview Questions

### Q1: What is a Docker volume?
**A:** A Docker volume is a persistent storage mechanism managed by Docker, stored in `/var/lib/docker/volumes/`. Volumes exist independently of container lifecycle, can be shared between containers, and are the preferred way to persist container data.

### Q2: What is the difference between named and anonymous volumes?
**A:** Named volumes have explicit names you assign (`docker run -v mydata:/path`), making them easy to manage, backup, and reuse. Anonymous volumes get random IDs, are created automatically, and are often orphaned. Always prefer named volumes.

### Q3: How do you share data between containers?
**A:** Mount the same volume in multiple containers: `docker run -v shared:/data container1` and `docker run -v shared:/data container2`. One container can write while others read (use `:ro` for readers).

### Q4: How do you backup a Docker volume?
**A:** Create a temporary container that mounts the volume and a host directory, then tar the contents: `docker run --rm -v mydata:/data -v $(pwd):/backup alpine tar czf /backup/backup.tar.gz -C /data .`

### Q5: What happens to a volume when you remove a container?
**A:** The volume persists - it's independent of the container. You can start a new container and mount the same volume to access the data. Volumes must be explicitly deleted with `docker volume rm`.

### Q6: What is a volume driver?
**A:** A volume driver determines where and how volume data is stored. The default `local` driver stores on the host filesystem. Other drivers support NFS, cloud storage (S3, Azure Files), or distributed storage systems.

### Q7: When would you use a volume vs a bind mount?
**A:** Use volumes for persistent application data (databases, uploads) - they're managed by Docker and portable. Use bind mounts for development (live code reload) or when you need access to specific host paths.

### Q8: How do you remove all unused volumes?
**A:** Run `docker volume prune` which removes all volumes not mounted by any container. Be careful - this is destructive. Add `-f` to skip the confirmation prompt.
