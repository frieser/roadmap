## Summary
The `terraform state mv` command is used to move items in the Terraform state. It allows you to rename resources or move them into/between modules without destroying and recreating the underlying infrastructure. This command is essential for refactoring Terraform configurations while maintaining the link between the code and existing remote objects.

## Detailed Explanation

### What and Why
In Terraform, the state file maps your code definitions (resource addresses) to real-world infrastructure. If you rename a resource in your `.tf` files, Terraform will normally see this as a deletion of the old name and a creation of the new name. `terraform state mv` intervenes in this process by updating the state to use the new name for the existing remote object.

### Common Use Cases
1.  **Renaming a Resource**: Change `aws_instance.web_server` to `aws_instance.frontend`.
2.  **Moving to a Module**: Moving a resource from the root module into a child module (e.g., `aws_instance.db` to `module.database.aws_instance.db`).
3.  **Refactoring Infrastructure**: Reorganizing state to match a new architectural pattern without downtime.
4.  **Moving between States**: Shifting resources from one state file to another (requires the `-state-out` flag).

### Basic Usage
```bash
# Rename a resource
terraform state mv aws_instance.old_name aws_instance.new_name

# Move a resource into a module
terraform state mv aws_instance.web module.app.aws_instance.web

# Move a resource from one state file to another
terraform state mv -state-out=destination.tfstate aws_instance.my_vm aws_instance.my_vm
```

### The Modern Alternative: `moved` Blocks
Since Terraform 1.1, the `moved` block is the preferred way to handle refactoring. Instead of running CLI commands manually (which are hard to track in version control), you define the move in your HCL:

```hcl
moved {
  from = aws_instance.old_name
  to   = aws_instance.new_name
}
```
Terraform will automatically handle the state migration during the next `plan`/`apply`.

### Go Application
In automation or custom tooling (like a migration script), you might need to execute state moves programmatically. Using Go's `os/exec` package is the standard way to interact with the Terraform CLI.

```go
package main

import (
	"fmt"
	"os/exec"
)

// MoveResource wraps the terraform state mv command
func MoveResource(oldAddress, newAddress string) error {
	fmt.Printf("Moving %s to %s...\n", oldAddress, newAddress)
	
	cmd := exec.Command("terraform", "state", "mv", oldAddress, newAddress)
	
	// Capture output for debugging
	output, err := cmd.CombinedOutput()
	if err != nil {
		return fmt.Errorf("failed to move state: %v\nOutput: %s", err, string(output))
	}
	
	fmt.Println("Move successful.")
	return nil
}

func main() {
	err := MoveResource("aws_s3_bucket.legacy", "module.storage.aws_s3_bucket.main")
	if err != nil {
		fmt.Printf("Error: %v\n", err)
	}
}
```

## Interview Questions

**Q: What is the primary risk of using `terraform state mv`?**
**A:** The primary risk is corrupting the state file if the command is interrupted or used incorrectly. It is highly recommended to take a backup of the state file (`terraform state pull > backup.tfstate`) before performing manual modifications.

**Q: How do you move a resource from one Terraform configuration (state) to another?**
**A:** You use the `-state-out` flag: `terraform state mv -state-out=other.tfstate source_address destination_address`. This removes the resource from the current state and adds it to the target state file.

**Q: Why would you use `terraform state mv` instead of just deleting and recreating a resource?**
**A:** Deleting and recreating infrastructure causes downtime and potential data loss (e.g., a database or an S3 bucket). `state mv` allows you to change the code structure while keeping the existing resource alive and managed.

**Q: What is the difference between `terraform state mv` and the `moved` block?**
**A:** `terraform state mv` is an imperative CLI command that modifies the state immediately. The `moved` block is a declarative HCL feature (Terraform 1.1+) that records the refactoring in code, making it version-controlled and repeatable across different environments (dev, staging, prod) during `terraform apply`.
