## Summary
Authentication in Terraform Cloud (TFC) and Enterprise (TFE) is multi-layered, supporting various identities from human users to automated pipelines. It leverages **API Tokens** at different scopes, **Single Sign-On (SSO)** via SAML for enterprise identity management, and **Dynamic Credentials** via OIDC to eliminate the need for long-lived static cloud secrets.

## Detailed Explanation

### 1. API Token Hierarchy
Terraform uses tokens to authorize CLI, API, and VCS interactions.
- **User Tokens**: Generated by individual users; inherit the user's permissions across all organizations. Best for `terraform login`.
- **Team Tokens**: Scoped to a specific team. Ideal for CI/CD pipelines (e.g., GitHub Actions) to perform runs without being tied to a personal account.
- **Organization Tokens**: Administrative tokens for managing organization-level resources like teams and workspaces. *Note: They cannot perform runs.*

### 2. Single Sign-On (SSO)
Enterprise environments typically integrate TFC/TFE with identity providers (IdPs) like Okta, Azure AD, or Ping Identity using **SAML 2.0**.
- **JIT Provisioning**: Automatically creates TFC accounts upon first login.
- **Team Mapping**: Uses SAML assertions to automatically place users into TFC teams based on their IdP groups.

### 3. Dynamic Credentials (OIDC)
Instead of storing AWS Access Keys or Azure Client Secrets in Terraform variables, TFC can use **OpenID Connect (OIDC)** to request short-lived, temporary credentials directly from the cloud provider.
- **Security**: No static secrets to rotate or leak.
- **Trust Relationship**: A trust is established between TFC and the Cloud Provider (AWS, GCP, Azure) based on the TFC run's identity.

### 4. Secret Management: Variable Sets
Variable sets allow organizations to manage common secrets (like provider credentials or global tags) in one place and apply them to multiple workspaces.
- **Sensitive Variables**: Marked as "Sensitive" in TFC to ensure they are masked in UI logs and API outputs.

### HCL Configuration Example

**Defining a Variable Set with Sensitive Secrets:**
```hcl
resource "tfe_variable_set" "common_secrets" {
  name         = "Global-Cloud-Credentials"
  description  = "Shared secrets for all production workspaces"
  organization = "my-org"
  global       = false
}

resource "tfe_variable" "aws_access_key" {
  key             = "AWS_ACCESS_KEY_ID"
  value           = var.aws_key
  category        = "env" # Environment variable for the provider
  sensitive       = true  # Masked in UI
  variable_set_id = tfe_variable_set.common_secrets.id
}
```

**Configuring OIDC Trust (AWS Example):**
```hcl
# In AWS, you create an OIDC Provider and an IAM Role
# In TFC, you set environment variables to trigger the OIDC flow
resource "tfe_variable" "enable_aws_oidc" {
  key          = "TFC_AWS_PROVIDER_AUTH"
  value        = "true"
  category     = "env"
  workspace_id = tfe_workspace.my_app.id
}

resource "tfe_variable" "aws_role_arn" {
  key          = "TFC_AWS_RUN_ROLE_ARN"
  value        = "arn:aws:iam::123456789012:role/tfc-role"
  category     = "env"
  workspace_id = tfe_workspace.my_app.id
}
```

### Go Application
When building custom automation, developers use the `go-tfe` library to manage these credentials.

```go
package main

import (
	"context"
	"log"

	"github.com/hashicorp/go-tfe"
)

func main() {
	ctx := context.Background()
	client, _ := tfe.NewClient(&tfe.Config{Token: "ORG_TOKEN"})

	// Create a new team token for a CI pipeline
	token, err := client.TeamTokens.Create(ctx, "team-xxxxxx")
	if err != nil {
		log.Fatal(err)
	}
	log.Printf("New Team Token: %s", token.Token)
}
```

## Interview Questions

**Q: What is the difference between a Team Token and an Organization Token?**
**A:** A Team Token is used to perform runs (plan/apply) in workspaces that the team has access to, making it ideal for CI/CD. An Organization Token is for administrative tasks (managing the org itself) and cannot be used to trigger runs or upload states.

**Q: Why is OIDC (Dynamic Credentials) preferred over static secrets?**
**A:** OIDC eliminates the risk of static credential leakage and the operational burden of secret rotation. It uses short-lived tokens that are only valid for the duration of a specific Terraform run.

**Q: How does "Sensitive" variable handling work in TFC?**
**A:** When a variable is marked sensitive, its value is encrypted at rest. TFC redacts the value in the web UI, API responses, and automatically scrubs it from the standard output of Terraform runs.

**Q: What is "Team Mapping" in the context of SAML SSO?**
**A:** It is the process of using SAML attributes (groups) sent by the Identity Provider to automatically assign TFC users to specific teams, ensuring that access control is managed centrally at the IdP level.
